# Offline feature analysis

Analyze an entire feature boundary before adding another native integration.
For the guest power wheel, the boundary covers input, movie initialization,
power/group population, slot assignment, caster selection, pause policy and
close-time tactical orders. A compiled hook is not a completed boundary.

Use the retained private feature dossier as the starting point. It joins named
native roles, cached call sites and completely decoded selected script exports.
The initial power-wheel dossier contains8 roles,34 script-export observations
and117 retained call instructions. These counts describe navigation coverage,
not117 resolved semantic relationships. Unknown indirect calls and incomplete
function boundaries remain explicit.

Prefer a bound Ghidra/REA session for pseudocode and call relationships. Initial
auto-analysis can outlive an MCP observation deadline. A timeout does not prove
the provider stopped: inspect its same run/process and progress log before
starting a replacement. Restricted process visibility is unavailable evidence,
not proof that the provider has no process. Reuse a live session and retain
complete returned evidence before extracting a bounded report.

If a CLI fallback is needed, use the installed public launcher, explicit local
provider/runtime paths and a private output file. Verify terminal completion,
successful result identity and target digest before treating the file as a
decompilation. An empty file, advertised capability or CPU activity proves no
pseudocode result. Do not repeatedly import the target while another analysis
is still progressing.

After analysis, produce one feature implementation with documented remaining
dependencies and lifecycle/restoration behavior. Rebuild native targets after
source edits. Keep source/build verification separate from later user-approved
gameplay validation; static analysis never proves casting, rendering, movement
or campaign continuity. Do not commit extracted game code or raw tool logs.
